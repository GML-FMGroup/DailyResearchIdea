# Independent Tool Verification via Perturbation-Injected Rollout Scoring for VLM Robot Coding Agents

## Motivation

Self-authored tool evaluation in VLM robot coding agents remains structurally unverified: HexaShell, Darwin Godel Machine, and AutoEval all rely on the agent's own diagnosis or task success as the acceptance signal, which conflates tool correctness with agent self-assessment. This shared residual gap persists because these systems dropped external evaluators while assuming self-diagnosis suffices, leaving no independent scoring or population-based selection to reject tools that overfit to the layouts the agent happened to observe. The structural problem is that a single self-authored tool is never tested against counterfactual perturbations it was not written to handle, so its acceptance reflects the agent's confidence rather than its robustness.

## Key Insight

A tool's robustness is identifiable from the variance of its success rate across a population of perturbation-injected rollouts that are generated by a fixed, task-agnostic perturbation operator and scored by an independent success detector, because this variance isolates the tool's sensitivity to input changes from the agent's self-diagnosis and from the task's base difficulty.

## Method

**What it is.** We introduce **ToolVerifier**, a thin harness component that takes as input a candidate tool (a small program authored by the VLM agent, e.g., a localization or grasping routine) and a set of held-out task layouts, and outputs an accept/reject decision. It does so by generating a population of perturbed tool variants, executing each on perturbation-injected rollouts, and scoring each rollout with a task-agnostic success detector that does not consult the agent's logs or self-diagnosis.

**Load-bearing assumption (stated explicitly).** The variance of success rate across perturbed tool variants, S_var, is a valid proxy for the tool's functional robustness to input changes. This requires that the perturbation operator P's support intersects the tool's executed failure modes on held-out layouts; if P perturbs only dead code paths or semantically inert operations, S_var reflects syntactic noise rather than functional fragility. We therefore add a coverage diagnostic (step 7) that reports the fraction of perturbed code paths actually executed, and we validate P against a labeled set of known-fragile vs. known-robust tools (experiment section).

**How it works.**

```pseudocode
# Input: candidate tool T authored by VLM agent, held-out layouts L_heldout (N=10), perturbation operator P, population size K=8, acceptance threshold tau=0.7
# Output: accept/reject decision for T, plus coverage diagnostic

1. Generate population of tool variants:
   for k in 1..K:
       T_k = P(T, seed=k)   # P injects a random syntactic/semantic perturbation: e.g., swaps a camera index, perturbs a threshold by +/-5%, reorders two geometric operations
   T_0 = T                    # include the unperturbed tool

2. For each variant T_k (k=0..K) and each layout l in L_heldout:
   for each perturbation-injected rollout r in Rollouts(l):   # Rollouts(l) = 5 rollouts per layout, each with a random object pose perturbation drawn from P_rollout
       execute T_k on r
       s_{k,r} = SuccessDetector(r)   # task-agnostic: checks whether the target object was moved to the goal region using only robot-observable state (joint angles, gripper state, known goal region geometry); no agent logs consulted

3. Compute per-variant success rate:
   S_k = mean_{r} s_{k,r}

4. Compute population statistics:
   S_mean = mean_k S_k
   S_var  = variance_k S_k

5. Accept T iff:
   (a) S_0 >= tau                       # unperturbed tool succeeds on held-out layouts
   AND
   (b) S_mean >= tau - 0.1              # population mean is not dragged down by fragile variants
   AND
   (c) S_var <= 0.05                    # low variance across variants: tool is robust to perturbation

6. Return accept/reject with the vector (S_0, S_mean, S_var) as the score.

7. Coverage diagnostic: for each perturbed variant T_k, record the set of code lines executed during rollouts on L_heldout. Compute coverage = (number of distinct lines executed across all T_k) / (total lines in T). Report coverage alongside the decision. If coverage < 0.8, flag the decision as low-confidence (S_var may reflect syntactic noise).
```

**Why this design.** We chose a population of perturbed tool variants over a single execution of the unperturbed tool because a single execution cannot distinguish a tool that is correct for the right reason from one that happens to work on the observed layouts; the population variance S_var operationalizes robustness, accepting the cost that K+1 executions per layout multiply evaluation time by (K+1). We chose a task-agnostic success detector that reads only robot-observable state (joint angles, gripper state, goal-region geometry) over the agent's self-reported logs because HexaShell's logs are produced by the same agent that authored the tool, so they inherit its blind spots; the cost is that the detector must be hand-specified per task family, limiting coverage to tasks with a checkable goal predicate. We chose a fixed syntactic/semantic perturbation operator P over a learned perturbation model because P must be independent of the agent's tool-writing distribution to avoid correlated failures; the cost is that P may miss domain-specific perturbations the agent would never think to test. We chose a conjunctive acceptance rule (S_0 >= tau AND S_mean >= tau-0.1 AND S_var <= 0.05) over a single scalar score because the three conditions separate correctness (S_0), population-level stability (S_mean), and robustness (S_var), accepting the cost that the thresholds tau and 0.05 must be calibrated per task family. A domain expert would not describe this as a variant of Darwin Godel Machine's evolutionary selection because DGM selects variants by their performance on the target task itself, whereas ToolVerifier selects a single tool by its sensitivity to a perturbation operator that is external to both the agent and the task; nor is it a variant of AutoEval, which uses the agent's own evaluation signal, because ToolVerifier's success detector never reads agent-produced signals.

**Why this measures what we claim.** The computational quantity S_var (variance of success rate across perturbed tool variants) measures tool robustness because the assumption that the perturbation operator P is independent of the tool's failure modes makes variance across variants equivalent to sensitivity to input changes; this assumption fails when P happens to perturb only code paths that are never executed on the held-out layouts, in which case S_var reflects irrelevant syntactic variation rather than functional fragility. The computational quantity S_0 (unperturbed success rate on held-out layouts) measures generalization because the assumption that held-out layouts are drawn from the same task distribution but disjoint from the layouts used during tool authoring makes success on them equivalent to out-of-sample correctness; this assumption fails when the held-out layouts are too similar to the authoring layouts, in which case S_0 reflects memorization rather than generalization. The computational quantity S_mean (mean success rate across variants) measures population-level stability because the assumption that the K perturbations are exchangeable draws from P makes the mean equivalent to expected performance under perturbation; this assumption fails when P is biased toward a subset of perturbations, in which case S_mean reflects performance under that biased subset rather than expected robustness. The success detector's task-agnostic predicate measures task success because the assumption that the goal predicate (target object in goal region) is necessary and sufficient for task completion makes the detector equivalent to ground-truth success; this assumption fails when the task has multiple valid goal configurations not captured by the predicate, in which case the detector reflects a narrower notion of success than the task requires.

## Experiment

### Evaluation Setup

| Role | Choice | Rationale (≤12 words) |
| --- | --- | --- |
| Dataset | HexaShell held-out layouts (10 per task) | Disjoint from authoring layouts; tests out-of-sample generalization |
| Primary metric | Tool acceptance precision on a manually verified tool pool | Directly measures whether accept decisions track real robustness |
| Baseline | Single-execution verifier (S_0 only) | Tests whether population variance adds signal beyond raw success |
| Baseline | Agent self-report verifier | Tests whether task-agnostic detector beats agent logs |
| Baseline | DGM-style target-task selection | Tests whether external perturbation beats target-task fitness |
| Baseline | Mutation-testing baseline (code-coverage-weighted failure rate) | Tests whether variance adds signal beyond standard mutation testing |
| Ablation-of-ours | ToolVerifier without perturbation population (K=0) | Isolates contribution of variant population statistics |
| Ablation-of-ours | ToolVerifier with coverage diagnostic disabled | Tests whether coverage flag affects precision |

### Why this setup validates the claim

The central claim is that a tool's sensitivity to an external perturbation operator, scored by a task-agnostic success detector, predicts whether the tool will generalize to held-out layouts better than existing selection signals. To falsify or confirm this, we need a tool pool with known ground-truth robustness: a set of candidate tools whose true held-out success rate we measure exhaustively, then check whether ToolVerifier's accept/reject decision correlates with that ground truth. The single-execution baseline isolates the value of the population variance S_var over raw S_0; if S_0 alone matches ToolVerifier's precision, the perturbation machinery is dead weight. The agent self-report baseline tests the task-agnostic detector claim: if self-reported logs select equally well, the detector design is unnecessary. The DGM-style baseline tests the external-perturbation claim: if selecting by target-task performance matches ToolVerifier, the perturbation operator adds nothing. The mutation-testing baseline tests whether the variance statistic adds signal beyond standard mutation testing: if code-coverage-weighted failure rate matches ToolVerifier's precision, the variance statistic is redundant. The K=0 ablation directly removes the population statistics, so any gap between it and full ToolVerifier is attributable to S_mean and S_var. The coverage-disabled ablation tests whether the coverage diagnostic affects precision, indicating whether low-coverage cases introduce noise. Acceptance precision is the right metric because the downstream cost of accepting a fragile tool (silent failures on new layouts) is exactly what the method claims to reduce; a tool that is rejected but would have generalized is a lesser cost, so we weight precision over recall. Additionally, we measure the correlation between perturbation-induced failures and held-out-layout failures across the tool pool; if this correlation is low, the S_var robustness claim is unsupported, so we report this correlation as a validity check on the perturbation operator.

### Expected outcome and causal chain

**vs. Single-execution verifier (S_0 only)** — On a case where a tool happens to succeed on all ten held-out layouts but only because it hard-codes a camera index that coincides with the correct view on those layouts, the single-execution verifier accepts it because S_0 is high and it never probes alternate code paths. Our method instead swaps the camera index across the population, so several variants fail and S_var spikes, triggering rejection. We expect ToolVerifier to show a noticeable precision gap on the subset of tools with coincidental-but-fragile success, with near-parity on tools that are robustly correct.

**vs. Agent self-report verifier** — On a case where the tool's own logging reports success because the agent's success predicate is written in terms of the same intermediate variables the tool manipulates, the self-report verifier accepts a tool that actually leaves the object outside the goal region. Our method instead reads only joint angles, gripper state, and goal-region geometry, so the discrepancy is caught. We expect the self-report baseline to accept a cluster of tools that ToolVerifier rejects, concentrated on tasks where the agent's log predicate and the true goal predicate diverge.

**vs. DGM-style target-task selection** — On a case where a tool overfits to the target task's observed layouts and scores highest on target-task fitness, DGM-style selection keeps it, because fitness on the target task is the selection criterion and the perturbation operator is absent. Our method instead scores the tool on held-out layouts under injected perturbations, so the overfit tool's variance exposes it. We expect DGM-style selection to exhibit a higher accept rate for overfit tools and a correspondingly lower precision, with the gap largest on tasks with high layout variability.

**vs. Mutation-testing baseline (code-coverage-weighted failure rate)** — On a case where a tool has high mutation score (many mutants killed) but the killed mutants are all in code paths not executed on held-out layouts, the mutation-testing baseline accepts it because coverage-weighted failure rate is high. Our method instead computes variance across variants that are actually executed on held-out rollouts, so S_var reflects functional fragility. We expect ToolVerifier to have higher precision on tools with high mutation score but low functional robustness, with the gap largest on tools with many dead code paths.

**vs. Ablation: ToolVerifier without coverage diagnostic** — On a case where the perturbation operator perturbs only dead code, the coverage diagnostic flags low coverage and the decision is marked low-confidence. Without the diagnostic, the decision is made with S_var reflecting syntactic noise. We expect the coverage-disabled ablation to have lower precision on tools with low coverage, confirming the diagnostic's value.

### What would falsify this idea

If ToolVerifier's acceptance decisions correlate with ground-truth held-out robustness no better than the single-execution S_0 baseline, or if its precision gain is uniform across all tool subsets rather than concentrated on the fragile-but-coincidentally-successful subset where the perturbation mechanism is predicted to act, then the central claim that external perturbation sensitivity measures robustness is wrong. Additionally, if the correlation between perturbation-induced failures and held-out-layout failures is low (e.g., <0.3), the S_var robustness claim is unsupported.
